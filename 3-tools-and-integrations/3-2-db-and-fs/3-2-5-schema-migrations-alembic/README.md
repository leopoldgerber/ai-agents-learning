# Migrations and Schema Versioning: Alembic (3.2.5)

## About This Lesson

This lesson introduces **database schema migrations** and **schema versioning** using **Alembic**.

In real agent systems, database schemas evolve continuously:

* new tables appear,
* columns are added or changed,
* indexes and constraints are introduced for performance and correctness.

The goal of this lesson is **conceptual understanding** of how schema migrations work and why Alembic is the standard tool for this task in SQLAlchemy-based projects.

No executable scripts are created at this step. This lesson focuses entirely on **mental models and architecture**.

---

## Why Schema Migrations Exist

Without migrations, schema changes are often applied manually using `ALTER TABLE` commands. This approach breaks down as soon as:

* multiple developers work on the same project,
* several environments exist (dev / staging / production),
* deployments must be reproducible and safe.

Schema migrations solve this by making **schema changes explicit, ordered, and versioned**.

---

## What Alembic Is

Alembic is a **schema migration and versioning tool** for SQLAlchemy.

Its responsibilities are:

* tracking schema versions over time,
* applying schema changes incrementally,
* reproducing the same schema state across environments,
* enabling controlled rollbacks during development.

Alembic works by applying **migration steps**, each representing a single structural change to the database.

---

## Migrations vs Schema vs Data

It is critical to separate these concepts:

* **Schema** — tables, columns, types, indexes, constraints.
* **Data** — rows stored inside tables.
* **Migration** — a step that transforms the schema from one version to another.

Alembic manages **schema evolution only**.

It does not manage:

* business data,
* data correctness,
* data transformation pipelines.

Mixing data manipulation with schema migrations is considered dangerous, especially in production systems.

---

## Schema Versioning Model

Alembic versions the schema using a **revision graph**.

Each migration:

* has a unique revision identifier,
* references its parent revision(s),
* forms a directed acyclic graph (DAG).

This model allows:

* parallel schema evolution,
* safe collaboration between developers,
* explicit resolution of branching through merge migrations.

The current schema version is stored directly in the database in the `alembic_version` table.

---

## Alembic and SQLAlchemy Models

Alembic does not infer schema intent automatically.

Instead, it relies on an explicit contract:

* SQLAlchemy models describe the **desired schema state**.
* Alembic compares this desired state against the **actual database schema**.

This comparison is driven by the `target_metadata` configuration, which defines which models represent the authoritative schema.

---

## Autogeneration Boundaries

Alembic can generate migrations automatically by comparing models and database state, but:

* autogenerated migrations must always be reviewed manually,
* some schema changes cannot be inferred safely,
* destructive operations (drops, type changes) require architectural caution.

Alembic prioritizes correctness and explicit developer intent over automation.
